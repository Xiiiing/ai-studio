# H3 自动提示词与有界返修

选择 H3 后，正常工作流会让**已配置的分镜导演模型**自动把批准镜头编译成 H3 提示词。用户填写故事与镜头要求，确认人物、画风和动作即可，不需要另写英文视频提示词。模型绑定、H3 质量档和采样参数继续由用户配置；本功能不安装或部署模型服务。

## 从批准镜头到视频

1. 分镜阶段确定剧情动作、人物／道具归属、运镜、连续性和时长，图像阶段提供首帧及已有审核结果。
2. 制作阶段显示“自动编写视频镜头提示词”，由 `storyboard_director` 的实际模型生成结构化计划：首帧状态、最多四段动作时序、结束状态、摄影机和连续性。编译专用模板为显式 `3.1.0`，普通分镜及团队安排的默认模板不变。
3. 程序验证字段、时间范围及从0秒到镜头结束的完整连续覆盖，统一渲染 Picture 1 在 0.00 秒的首帧锚点，以及 `integrated_multimodal_description`、`overall_soundscape`、`non_diegetic_music` 三段文本，并将这段真实提示词提交给 H3。
4. 视频生成后继续执行原有技术检查与配置的视觉审核。审核比较批准动作和画风，不把提示词编写成功当作画面通过。
5. 审核不合格时，工作流根据问题代码、原批准事实和正向约束重新编写提示词；需要新首帧时先完成首帧返修，再按实际新首帧校验和编译。达到原有次数或预算限制、审核不可用或动作无法忠实表达时暂停，已有媒体保留。

官方资料依据：[MiniMax 的本地 Context-IR 建议](https://github.com/MiniMax-AI/MiniMax-H3#h3-context-ir)、[基础提示指南](https://huggingface.co/MiniMaxAI/MiniMax-H3/blob/main/docs/VIDEO_PROMPT_WRITING_GUIDE_base_en.md)、[Comfy H3 提示指南](https://docs.comfy.org/tutorials/video/minimax/minimax-h3-prompt-guide)。本地编译采用首帧锚定、可见动作时序、明确运镜和声音策略；不是托管 Context-IR 的实现或同等质量承诺。BasicGuider 没有独立有效的负向提示分支，最终模板优先使用正向画面约束。

## 配置

在应用配置的 `production` 中选择：

```json
{
  "production": {
    "h3_prompting": "automatic"
  },
  "llm_roles": {
    "storyboard_director": "my_local_director"
  }
}
```

这是配置片段；`my_local_director` 必须是 `llm_profiles` 中已有且启用的真实连接，不能整段覆盖完整配置。H3 应用工作流未填写 `h3_prompting` 时默认 `automatic`。其他视频提供商不启用本编译器。

高级使用者可设置 `manual`，直接使用已经批准的 `motion_prompt` 和旧版拼接逻辑。直接调用低层 `ProductionEngine/_Run` 的兼容调用者维持原行为；显式启用自动模式时必须提供该批次的导演配置。正常 Web/worker 工作流会冻结并传入这份配置，不要求用户手写它。

对白和配乐继续由现有音频工作流负责，H3 提示仅选择静音或环境声，原生配乐为 None；当前适配器输出视频轨，不自动接管 Qwen3-TTS 配音。同步口型要求与此模式冲突时明确暂停，不悄悄改成闭口画面。H3 镜头沿用实际适配器的 1–15 秒限制。

## 恢复、缓存与证据

提示词在 H3 GPU worker 启动前准备，文本模型请求不占着 H3 双卡租约。模型不可用、格式错误或导演报告不可执行时，不回退通用提示词、不提交视频；第一次提示编写失败也不消耗视频尝试次数。首帧返修后的提示编写故障会保留 `prompt_preparing`，恢复同一 take 和已生成首帧。

已编译待执行、已提交或已生成的任务复用保存的真实提示词，未知提交先恢复确认。未生成任务按当前编译器实现和模板准备；导演模型、动作、连续性、首帧、画风或参数变化会使对应旧缓存失效。已生成视频按下述历史身份兼容规则核对，不能绕过未确认任务。原有视频人工选择在动作／连续性计划变化后需要重新确认。

首帧的审核评语、分数、审核模型或上下文容量变化只能影响审核，不改变视频生成身份。旧版把完整首帧 QA 纳入生成签名的素材，通过保存的首帧 QA 重算旧签名，并核对全部当前生成输入后兼容复审；实际首帧字节、镜头、导演、参数或重制版本变化仍会使缓存失效。兼容复审保留原始 `source_signature`，另记稳定的 `generation_signature`，不改写历史生成归属。文件仍须通过校验和检查。

已锁定的生成成果允许复审；若原始生成回执还没有来源及计划签名，可在文件路径、校验和及全部锁定输入保持一致时一次性补齐。已有的来源/计划签名、素材和输入仍不可更换，复审失败后的新生成也仍受锁保护。

首帧审核只要求能够承接批准动作的初态，不能要求单帧证明睁眼或特效逐渐出现的过程。当前镜头的动作和过程性连续性只进入视频审核，首帧仍保留其他镜头的时序，用于检查道具提前出现等矛盾。特效边缘、粒子形状等未改变关键叙事含义的差异记为 minor；文字问题须有实际可读内容的证据。最终结论按 blocking 问题、配置的最低分、指定画风和素材匹配门判定，保留 `model_status` 供核对原模型结论。低分、错误身份/道具、严重崩坏及视频批准动作未兑现不会因此放行。

`attempt.json` 和视频结果回执保存 `h3_prompt`：实际模型身份、模板／实现指纹、结构化计划、输入签名、首帧 SHA-256、最终提示词哈希及尝试号。候选接口继续显示实际提示词，并附编译回执。`quality_status=pending_actual_media_review` 只表示编译完成，实际媒体质量看视频 QA。

## 已验证与限制

CPU 回归覆盖真正的本机 TCP/HTTP 文本接口调用、模型身份校验、结构化协议、错误处理、缓存与恢复，以及使用真实 CPU 媒体的生产循环：编译发生在 GPU 租约外、文字进入 H3 图、返修更新首帧和提示词、旧视频锁定复审、策略更新后旧失败素材仅重新审核一次。未改变生成输入的复审不创建新 take，也不重置原次数或预算。

文本导演没有直接看到首帧像素，使用批准画面描述、实际首帧标识及已有视觉 QA 线索；画面左右不等于人物自身左右，资料不明确时沿用原持物手描述。构图与动作忠实度仍依赖实际视频审核，文字检查不能保证画面美感、手部正确或动作完整。

本轮另以隔离镜头验证实际配置的导演、Wkp H3 和视觉审核调用，不修改正式项目剧情或重新生成正式项目已有视频。实际效果与部署记录见对应 PR 的验证说明，不能把模拟测试计数当作真实模型质量证明。

## 分时段动作与连续帧补审

新版自动导演采用已实测的 B 写法：每段说明动作执行者、身体部位、方向/幅度和到达姿态，描述道具随原持物手的路径及衣袖、发梢等余动。只细化批准动作，保持批准风格、人物、机位和剧情；已经完成的首帧姿态不从零重做，静止配角不被强制加动作。

稀疏审核明确标注真实时间及抽样间隔。对动作、连续性或低质量疑点，以及无法确认人物运动的结果，最多补查两个窗口，每个窗口最多十二张原视频连续解码帧。像素差仅用于选取窗口，不用于判定人物动作或质量。视觉模型需引用同一窗口内连续区间的起止帧（所有中间帧均已提供），独立重新评审；确认的缺陷及未核验的身份、道具、画风等错误继续阻断。窗口不足、上下文不足、证据引用不合法或结论矛盾时保留视频待补审，不把缺少抽样中间帧当作原视频缺帧，也不自动放行。

提示词政策升级只影响新制作；已生成视频可按已存编译器身份重算完整输入签名后复审，保留原视频和提示词。真实剧情、首帧、模型/采样参数或显式重拍变化仍会使旧候选失效，锁定成果不会自动重生成。旧模板 `3.0.0` 保留用于历史回执验证。

审核策略变化后，技术检查已通过、生成输入和结果回执一致的旧失败素材可以直接复审一次；新结论会保存当前审核签名，同一策略不循环补审。技术失败、文件损坏、输入变化或无来源的记录不能因此复用。

## 已有视频仅复审与静态空间关系核验

自动 H3 批次默认 `review_only_existing_videos=true`：首次批次已有结果回执的视频只能复用或审核，保护清单随检查点持久化，远程 GPU 等待恢复不重新划分新旧视频。项目恢复请求可携带 `review_only_existing_videos: true`，将恢复时的全部既有视频重新固定为只复审；原预算和尝试记录保留。复审失败直接产生 `existing_video_review_failed` 人工处理关卡，保存分数、问题及原视频；同一审核策略再次恢复不会重审失败项，也不会进入 GPU、提示词或首帧返修分支。输入变化且无法安全复用时产生 `existing_video_review_required`，而非偷偷重拍。视频锁作为额外保护继续有效。当前批次首次生成的视频仍可使用原有有界返修；只有明确授权自动重制的调用者才设置 `review_only_existing_videos=false`。

静态首帧出现接触、能量连接等阻断争议时，最多调用一次局部细节核验：保留全部参考和完整候选 F0，同时提供同一原文件的两块原始像素裁剪 C1/C2 及坐标。模型须结合全图和局部指出可见证据，区分躯干/后肩与头发/前肩、手掌与腕部、特效斑点与珠宝；不能以裁剪外区域证明对象不存在。确认的错误和未核验的身份、道具、画风门继续阻断；证据不清、引用无效或上下文不足保留素材待补审。裁剪本身不决定通过，不降低分数线或强行消除真实接触错误。

接触镜头的图像 prompt 与逐镜人物 position 应描述同一位置及同一只手。能量线须说明相同接触点与持物状态，特效标记应避免与手指/饰物混淆；审核按这些批准事实判断，不自行增加全链路无遮挡的要求。修改空间构图仍通过既有镜头编辑、版本与预算机制，不直接改写旧素材或审核结论。

## 首帧返修与原批准动作复审

图像返修和生成视频项目的首帧审核共用 `review_contracts.starting_frame`：只保留批准的静态画面与人物初始位置、持物等状态，排除完整 `action`、`motion_prompt`、过程性 `continuity`、戏剧节拍和人物 `story_state`。图像返修明确限定为起始帧，不把“借力站起”的终点混入“单膝跪地准备起身”的画面。完整动作和连续性仍进入视频提示与视频审核，不能因拆开首帧契约而省略视频动作。

视频复审以本镜原批准的 `action` 和 `motion_prompt` 为动作要求，不套用后来导演模板的动作幅度，也不把“紧张、支撑、结印”等情绪或持续状态自动扩写成迈步、大幅挣扎或位移。人物、物体、相机和能量特效运动仍分别检查；细微动作需要实际跨时间证据，明确缺失的批准动作仍阻断，证据不足保留待审。

连续帧补证策略为 `continuous-frame-challenge.v2`。针对 `camera_only` 或不确定的运动判断，最多两个连续窗口分别覆盖前、后半段的可见变化，避免后半段强光效或运镜占满取证窗口、遗漏早段手部变化。每个窗口仍由原视频的相邻解码帧组成，不插帧、不以像素变化直接判定动作合格。

这些改动只影响提示词编译与审核取证，不自动放行素材。已有视频保持仅复审边界；失败或输入不匹配转人工节点，不请求导演、GPU 或新视频 take。达到首帧重试上限的镜头，需要用户明确授权的逐镜图像返修版本才能继续，不清空历史次数或账本。
